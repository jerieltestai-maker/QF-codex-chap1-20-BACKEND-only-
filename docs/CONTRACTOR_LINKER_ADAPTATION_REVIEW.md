## The useful core to carry forward

CL had a strong idea: each action changes what the CM, contractor, MCST, and admin can see and do next. QuoteFix needs that discipline from request through final invoice, but with fewer mandatory steps. Treat a job as a set of versioned decisions, evidence, and permissions rather than a long chain of screen labels. Build the ordinary one-off job first; add exception handling where an ordinary job can actually get stuck.

## Proposed normal flow and exception seams

This is a planning model, not a final state-machine decision:

1. **Request:** CM records the problem, evidence, known conditions and priorities. AI suggests factual structure; CM edits and approves. A manual route works. No mandatory three-file/video gate unless separately justified by pilot evidence.
2. **Quotation:** eligible contractors receive a redacted RFQ and submit sealed quotes. CM sees identities by default unless MCST disables that view. Initial quote precedes any site-visit request. Material RFQ edits create a new version and alert existing quoters; the policy for whether they must reconfirm is a later detailed decision.
3. **Selection and authorization:** CM selects a specific quote version with a rationale, closing quotations irreversibly. Below threshold this authorizes work; above threshold a named MCST decision is required. Rejection ends the ticket; a different contractor requires a new ticket.
4. **Delivery:** contractor records brief progress and ETA changes, requests variations before they take effect, and claims completion with photos and an invoice. CM reviews against the selected quote and approved variations. Concerns and remedies remain on the same job with immutable rounds.
5. **Close:** a named MCST user confirms one final-invoice version after review and any needed variation approval. That event freezes the amount, closes the job, assesses the two confirmed 4% fees, and starts the separate three-day deadline. Later financial changes use the still-open post-confirmation adjustment policy.

Use an explicit **capability matrix** for each transition: who may act, on which estate/job/version, what evidence and rationale are required, what is frozen, who must be notified, and what remains possible afterward. Model quotation, work authorization, execution, invoice review, and cancellation separately. One giant `ticket.status` enum would mix independent facts and recreate CL's dead ends. Ordinary commands need transaction boundaries, expected versions for competing edits, and idempotency for retries. Read models must respect each role's visibility, including files and exports.

## What was poorly designed in CL

1. **Mandatory evidence and ceremony outgrew the small-job use case.** Three media files including video, three AI sufficiency scores, a five-step wizard, seven sequential milestones, and a 12-question vetting form made every repair act like a major project. They also made AI failure and minor missing evidence into avoidable workflow barriers (CL 10:22 §6.2, §6.6–6.7; CL 11:00 §7, §9–10). QuoteFix should capture enough information to price safely while letting a CM report a real issue quickly.
2. **Displayed policy was not enforced policy.** CL priority weights did not affect sourcing, ±15% checks were inconsistent across revision paths, a five-day escalation existed only in copy, and “private” information or blind identities could leak via APIs and notifications. The old PRDs explicitly record these defects (CL 10:22 §10/§19; CL 11:00 §8/§28). QuoteFix should never promise a control before the server, files, and notifications enforce it.
3. **The lifecycle had dead ends.** A CM could raise a quality concern but the unique verification row prevented another review; some payment disputes had no escalation; a contractor could claim completion and the ticket could be called “closed” while the state remained elsewhere. A status change could remove the screen showing the dispute verdict (CL 10:22 §10.3/§19). QuoteFix needs response, remedy, escalation and correction paths for every negative outcome.
4. **Money and authority were conflated.** CL calculated invoices on read from mutable profile/tax data, trusted client totals, called authorization “payment,” allowed broad admin status rewinds, and treated one deduction as a refund transaction. QuoteFix's final payable amount, GST declaration, frozen invoice version, named MCST confirmation, fees, and adjustments need distinct records. Do not import CL's GST toggle, one-deduction rule, payment release flow, or 9% constant as product rules (CL 10:22 §6.9–6.10; CL 11:00 §11–12).
5. **Reputation was built before a sound evidence base.** It combined AI scoring, seven axes, tiers, flags, quarterly jobs, locks, damping, overrides, peer averages and admin dashboards while job counters could be stale, events could be dropped and unscored contractors held a default numeric 50. A large synthetic seed made the UI look mature without real outcomes (CL 10:22 §12/§18; CL 11:00 §14/§25). QuoteFix should make rating evidence and corrections reliable first, then design a scoring model from pilot data if one is warranted.
6. **The old data model made routine changes unsafe.** Condo identity was a repeated name string, actor IDs were client-supplied, dispute state lived in prose, media lived in public paths or database data URLs, and migrations could not reliably create a fresh database (CL 10:22 §3–4/§18–19; CL 11:00 §25/§28). QuoteFix should begin with estate IDs and memberships, verified server identity, typed records, private storage, and a clean migration history.
7. **Seeds and tests targeted spectacle before core correctness.** CL's reputation seed reset many prefixed rows, created about 50 synthetic contractor scenarios, and used predictable demo passwords, while tests did not cover the central ticket-to-close path (CL 10:22 §18.3–18.6). QuoteFix should have small isolated scenario fixtures and prove its core transitions before adding elaborate demo analytics.

## Blueprint work to finish before building

1. **Freeze a QuoteFix-only product contract.** Actor and permission matrix, core terms, must-have versus later scope, and explicit open policies. Preserve owner decisions from `OPEN_DECISIONS.md`; do not insert CL constants as defaults.
2. **Draw one lifecycle and exception map.** For each action, specify preconditions, affected version, recipient visibility, audit record, notification, undo/repair path, and UI next action. Include rejection, withdrawal, no quotes, failed AI, rejected variation, remedy, invoice dispute, and cancellation.
3. **Define financial snapshots.** Selected quote, authorized variations, each invoice version, confirmed invoice, two fee assessments, and post-confirmation adjustment. Make all threshold and fee calculations reproducible from frozen amounts.
4. **Define visibility and evidence.** Estate membership, contractor eligibility, quoted-price visibility, identity/address reveal, original versus redacted media, and export redaction. Verify each at API and file access level.
5. **Choose the smallest technical skeleton.** A single modular server application with relational data, private objects, durable background jobs for genuinely asynchronous work, migrations from an empty database, and one audited command path for each important transition. Add no separate reputation service or generalized rule engine for the first release.
6. **Design test fixtures with the workflow.** One small scenario per critical transition/exception, deterministic clock and IDs, disposable database guard, and a separate opt-in visual demo dataset. Production startup must never seed invented jobs or reputation. Acceptance should cover request → quote → selection → authorization → variation → completion → review → MCST invoice confirmation → export, plus the dead-end cases above.
