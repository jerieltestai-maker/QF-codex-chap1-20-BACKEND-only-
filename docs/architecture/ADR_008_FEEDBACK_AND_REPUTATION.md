# ADR 008 — Feedback, aftercare and reproducible reputation

Accepted for the authorised local build, 18 October 2026. Owner decisions in PRODUCT_MEMORY.md and OPEN_DECISIONS.md override earlier scoring proposals. This record complements ADR 006–007.

Durability is a job-linked obligation, not a lifecycle stage. Schedule it from the applicable complete settlement anchor and preserve instant/date precision. A pending correction reschedules the obligation; a completed observation keeps its original observation date and an audit of subsequent anchor changes. Notice delivery starts the response clock. Submission is atomic with evidence, task completion, audit and idempotency receipt. Closure does not depend on feedback.

Aftercare links into shared Admin Support but retains a dedicated physical-remedy engine. Shared case commands cannot resolve or bypass that engine. Each physical correction allocates the next retained completion round, requires inspection of that exact round and then Admin verification. Explanation-only outcomes require their own evidence. Preserve the original invoice/payment/fee cycle; new financial changes use the financial support workflow. Cancelled work is eligible only through the explicit performed-work settlement anchor supplied by Chapter 14; never infer performed work from a zero amount.

Evidence versions, moderation decisions, replies, calculations and selected comparison evidence are immutable. A correction needs fresh moderation; an old approval cannot publish new text. Public projections exclude referee contacts, private moderation reasons and identity-bearing free text where identities are concealed. Voided entries remain readable on grey with legible text and no public exclusion label. Redaction changes the published text without silently altering numerical answers.

Formula reputation-2026-10-18-v1 uses exact rational arithmetic and rounds once to one decimal. Map responses 1–5 to 0/25/50/75/100. Four dimensions each weigh 1, recommendation 1.2, and assessable, approved, uncontested durability 1. Normalize within a job, then average one unit per job. Include independently verified complete external references only when five eligible references exist; each reference and job then has equal weight. Apply normalized primary 1.25 and secondary 1.10 multipliers only to applicable rubric dimensions. Current price/availability remain current quote facts. Missing history and unavailable/contested durability never become favourable points.

Snapshots include formula configuration, eligible evidence versions, moderation IDs and source counts. Their fingerprint changes with eligible evidence or moderation. Comparisons recheck that fingerprint before committing advice or selection. A selected snapshot stays immutable and is projected through the reader's current access/masking rules.

Advice has a factual local implementation and an opt-in Gemini adapter. Authenticate, check CSRF/access/version/confirmation and replay idempotent results before any provider call. Call outside the database transaction, bound time/input/output, recheck the evidence afterwards and use server-written explanations. Share concurrent identical evaluation calls and reuse saved results for unchanged evidence/provider/context. Provider failure or unsupported output leaves factual comparison and manual choice available. No automatic retries or model upgrades incur additional calls.

Gemini receives short anonymous candidate IDs, current numerical quote facts and approved score/count summaries. It receives no names, job IDs, raw references, observations, documents or private notes. Output permits only candidate IDs/citations and must agree with supported factual ranking. The key stays in an ignored server file, never browser code or a URL. One fictional live check passed for gemini-3.5-flash-lite; mocked tests cover privacy, malformed output and cost boundaries.

Late assessable observations count with the actual observation date. First-month fault/callback percentages and specialty-strength labels remain unavailable pending owner rules. A Chapter 20 completion checkpoint and milestone reminder preserve the requested revisit. Warranty automation, retention policy and production release remain separate decisions/checks.

Validation and explicit limits are recorded in [the build evidence](../implementation/CHAPTERS_15_16_BUILD.md). Local SQL tests use PGlite; a server PostgreSQL and production release exercise are still required.
